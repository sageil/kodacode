KodaCode is a CLI coding assistant with a terminal UI and HTTP API. Built in Go, it connects to multiple AI providers and gives the model direct access to your codebase through 22 built-in tools: file operations, shell commands, code search, LSP queries, git integration, and more.

## Two Ways to Work

KodaCode ships with two primary agents that represent different development workflows. Switch between them with `Tab` or the `/agents` picker.

### Engineer: Explore, Plan, Execute

For complex tasks, the engineer follows a structured cycle:

1. **Explore**: spawns read-only explorer subagents to research your codebase in parallel
2. **Plan**: delegates to the planner agent, which creates numbered tasks with What, Where, How, and Risk for each step
3. **Approve**: presents the plan for your review. The engineer cannot edit files until you approve it.
4. **Execute**: works through the plan step by step and runs tests to verify each change

This is the right mode when a task touches multiple files, requires understanding existing architecture, or when you want to review the approach before any code changes.

```
> Add rate limiting to all API endpoints
# Engineer explores → finds 14 endpoints → planner creates 5-step plan → you approve → engineer executes
```

### Builder: Direct Implementation (default)

The default agent. For straightforward tasks, the builder skips the planning overhead. It reads code, understands it, and makes changes immediately. There are no subagents and no approval gates. It has the same tools as the engineer except for subagent delegation.

```
> Fix the nil pointer in handler.go line 42
# Builder reads the file, edits the line, runs tests. Done.
```

Use the builder when the task is clear and you don't need a plan: quick fixes, one-file edits, targeted changes across a few files.

### Adviser: Read-Only Research

A third primary agent for when you want analysis without modification. It explores your codebase, compares approaches, and gives recommendations without touching any files.

```
> How should I structure the caching layer?
> Compare REST vs GraphQL for this use case
```

All three are available via `Tab` cycling. See [Agent System](/features/agents/) for subagents (explorer, planner, polish, refactor, insight) and custom agent definitions.

## Configurable at Every Layer

KodaCode is designed to be configured, not locked down. Key things you control:

| What | How | Why it matters |
|------|-----|----------------|
| **AI provider & model** | `providers` + `/models` picker | Use any provider. Switch mid-session. Mix cloud and local models |
| **Utility model** | `utility_model` in config | Route cheap tasks (titles, compaction, research) to a fast model to cut cost |
| **Budget caps** | `session.budget` | Hard dollar limit per session. Stops the tool loop when exceeded |
| **Reasoning effort** | `/variant` or `thinking_budget` per model | Control how much the model "thinks": low for simple tasks, max for harder ones |
| **Sandbox boundaries** | `allowed_paths` + `ignore_patterns` | Every tool is confined to your project directory by default. Expand as needed |
| **Permissions** | `permission` with glob patterns | allow/ask/deny per tool, per file pattern, per agent. `rm *: deny` blocks deletes |
| **LSP servers** | Auto-discovered + `lsp.servers` | Code intelligence for any language. Zero config for Go, TypeScript, Python. Add more manually |
| **Diagnostics** | Auto-detected linters + `diagnostics.linters` | Linters run after every edit. Auto-detected from your project or configured explicitly |
| **Context management** | `compaction_threshold`, `prune_protect_tokens` | Tune when and how aggressively context is pruned and compacted |
| **Agents** | Markdown files in `.kodacode/agents/` | Define custom agents with specific tools, permissions, models, and system prompts |
| **System prompts** | Markdown files in `~/.config/kodacode/prompts/` | Override per agent, per provider, or per model |
| **MCP servers** | `mcp.servers` in config | Extend with any MCP-compatible tool server |
| **Themes** | YAML files in `~/.config/kodacode/themes/` | Every color in the TUI is configurable |

See [Configuration Reference](/reference/configuration/) for the complete config.yaml spec.

## How It Works

When you send a message, KodaCode:

1. Builds a system prompt from agent instructions, project context (`KODACODE.md`), memories, and pinned instructions
2. Sends your message to the configured AI model
3. The model responds with text and/or tool calls
4. Tool calls execute in parallel, including reading files, running commands, and searching code
5. Diagnostics run automatically on any edited files
6. Results feed back to the model for the next iteration
7. The cycle continues until the model has a final response

Everything streams in real time. You can watch tool calls execute, diffs render, and the response build as it happens. The sandbox checks every file path and command before execution. Leaving the project directory requires your permission.
