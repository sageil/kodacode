Configuration files are loaded in order, with later sources overriding earlier ones:

1. `~/.config/kodacode/config.yaml`: global defaults
2. `./kodacode.yaml`: project-specific overrides

Environment variables (`${VAR_NAME}`) are expanded automatically in `api_key`, `base_url`, `env`, and `headers` fields.

## Merge Behavior

Global config is loaded first, then project-local `kodacode.yaml` is merged on top. Merge behavior is field-specific:

| Shape | Behavior | Examples |
|-------|----------|----------|
| Scalars and simple nested fields | Override when the field is present in project config | `default_agent`, `session.max_retries`, `tui.auto_resume` |
| Keyed collections | Merge by stable key; matching entries are replaced or merged by field rules | `providers` by `id`, `mcp.servers` by `name`/`command`, `lsp.servers` by `name`, `session.models` by model key, `skills.models` by model key |
| Additive lists | Appended uniquely to the inherited value | `allowed_paths`, `ignore_patterns` |
| Ordered lists | Replaced wholesale | `fallback_models`, `instruction_files` |

Some keyed collections have additional field rules:

- `lsp.servers`: project entries merge field-by-field with the inherited server of the same `name`.
- `skills.models`: `allow_all` uses the project value when present; `deny` lists are appended uniquely.
- `permission`: merged per tool at the pattern level. Patterns from all layers are concatenated (defaults first, then global, then project or agent). The last matching pattern wins, so project patterns override inherited ones for the same glob while preserving unmentioned patterns. String shorthand rules such as `bash: allow` are expanded to `* → allow` before merging.

## Providers

```yaml
providers:
  - id: anthropic
    api_key: ${ANTHROPIC_API_KEY}          # leave empty for OAuth
    thinking_budget: 10000                 # default for all models from this provider
    thinking_type: adaptive                # "adaptive" (default) or "enabled"

  - id: openai
    api_key: ${OPENAI_API_KEY}
    models:                                 # optional static model definitions
      - id: custom-model
        name: Custom Model
        context_size: 128000
        thinking_budget: 8000              # per-model reasoning token budget

  - id: google
    api_key: ${GOOGLE_API_KEY}             # leave empty for OAuth
    models:
      - id: gemini-3-pro-preview
        thinking_budget: 10000             # enable thinking for this model

  - id: groq
    api_key: ${GROQ_API_KEY}
    base_url: https://api.groq.com/openai/v1

  - id: ollama
    base_url: http://localhost:11434/v1    # local models auto-discovered

  - id: lmstudio
    base_url: http://localhost:8000/v1     # local models auto-discovered
```

### Thinking type (Anthropic OAuth only)

The `thinking_type` field controls how thinking is injected for Anthropic OAuth/subscription requests:

| Value | Behavior |
|-------|----------|
| `adaptive` (default) | Model decides how much to think based on query complexity. More token-efficient. |
| `enabled` | Fixed token budget from `thinking_budget`. Predictable but uses more tokens. |

```yaml
# Adaptive: model decides thinking depth (recommended)
providers:
  - id: anthropic
    thinking_type: adaptive

# Fixed budget: always reserve 10K tokens for thinking
providers:
  - id: anthropic
    thinking_type: enabled
    thinking_budget: 10000
```

When `thinking_type` is `adaptive`, the `thinking_budget` is ignored for OAuth requests (the model decides). When `thinking_type` is `enabled`, the `thinking_budget` sets the token budget (defaults to 10,000 if not specified).

### Per-model thinking budget

The `thinking_budget` field controls reasoning tokens. Models without this field do not use extended thinking. Priority order:

1. **Agent frontmatter** `reasoning_budget` (highest)
2. **Variant toggle** (`/variant` cycling low/high/max)
3. **Per-model config** `thinking_budget`
4. **Provider-level** `thinking_budget`

## Models

```yaml
utility_model: anthropic/claude-haiku-4-5-20251001  # for background tasks (titles, compaction)
reviewer_model: anthropic/claude-sonnet-4-6         # for the reviewer subagent (defaults to utility_model)
default_agent: builder                              # agent for new sessions

fallback_models:                                    # tried in order when primary fails
  - anthropic/claude-sonnet-4-6
  - openai/gpt-4o
```

The model for each session is selected via the `/models` command or the model picker on the home screen. The `utility_model` is used for lightweight background tasks (title generation, context compaction) and by agents configured with `model: utility`. When not explicitly set, KodaCode auto-discovers the cheapest text-capable model across all configured providers. If the selected utility model fails permanently, the next ranked candidate is tried automatically. The `reviewer_model` (format: `provider/model-id`) is used by the reviewer subagent; if not set, it defaults to `utility_model`.

## Session

Session settings control three practical parts of daily use: how aggressively KodaCode spends tokens, how much it can do autonomously before checking with you, and how much recovery or observability you have when a session goes off the rails.

```yaml
session:
  compaction_threshold: 0.8     # compact at 80% of context window
  compaction_keep_turns: 10     # preserve last 10 turns after compaction
  prune_protect_tokens: 40000   # protect last 40K tokens from pruning
  prune_min_savings: 20000      # only prune if saves 20K+ tokens
  context_limit: 0.9            # stop tool loop at 90% of context
  max_retries: 5                # retry transient provider/API failures
  tool_call_argument_timeout: 60  # good default for hosted providers; raise for local models
  engineer_review_limit: 3      # reviewer reruns before asking you what to do
  engineer_execution_retry_limit: 6 # stalled-task nudges before asking you what to do
  max_subagents: 10             # max concurrent subagent sessions
  subagent_timeout: 5           # minutes before a subagent is cancelled (default: 5)
  plan_approval: true           # require user approval before executing plans (default: true)
  background_auto_react: true   # auto-prompt model when background task completes
  snapshot: false               # enable per-turn git snapshots (/replay to navigate)
  trace: false                  # enable per-turn trace capture for /cost and /trace
  primary_max_steps: 250        # max tool calls per primary turn (default: 250)
  subagent_max_steps: 30        # max tool calls per subagent turn (default: 30)
  budget: 0.0                   # max dollars per session (0 = unlimited)
  budget_warn: 0.0              # warn at this fraction of budget (0 = disabled)
  total_budget: 0.0             # max dollars across all non-ephemeral sessions
  total_budget_warn: 0.0        # cross-session warning threshold (0 = disabled)

  # Per-model overrides
  models:
    anthropic/claude-opus-4-6:
      compaction_threshold: 0.7
      prune_protect_tokens: 30000
      context_limit: 0.92
    openai/gpt-5.4:
      compaction_keep_turns: 6
      context_limit: 0.95
    ollama/qwen2.5-coder:
      tool_call_argument_timeout: 900 # slower local model: allow 15 minutes
```

Some of these values are stored as `0` or `nil` in config and pick up runtime fallbacks when left unset. The table below lists the effective behavior you get if you omit the field entirely.

| Field | Effective Default | What It Controls | Practical Value |
|-------|-------------------|------------------|-----------------|
| `compaction_threshold` | `0.8` | When older history is summarized into a compact session summary | Lower it for long or expensive sessions to keep input costs flatter. Raise it when preserving raw recent history matters more than token efficiency. |
| `compaction_keep_turns` | `10` | How many recent turns stay verbatim after compaction | Increase it when recent tool outputs and conversation nuance are important, especially in long refactors or debugging sessions. |
| `prune_protect_tokens` | `40000` | Tail of history protected from automatic tool-output pruning | Increase it when you want more recent file reads and command output to stay visible. Lower it to reclaim context earlier. |
| `prune_min_savings` | `20000` | Minimum savings before pruning happens at all | Lower it if smaller pruning wins still matter in verbose sessions. Raise it if you only want pruning to happen when it buys back a lot of room. |
| `context_limit` | `0.9` | Point where KodaCode stops tool calls and forces a final answer | Lower it for fragile providers or local models that struggle near the limit. Keep it high when you want the model to push further before stopping. |
| `max_retries` | `5` | Retries for transient provider/API failures | Raise it for flaky providers or rate-limit-heavy workflows. Lower it if you prefer fast failure over waiting through repeated retries. |
| `tool_call_argument_timeout` | `60` seconds | How long KodaCode waits for a model to finish streaming one tool call's JSON arguments | This is the general default for hosted providers. If you use slower local models in LM Studio or Ollama, raise it so valid tool-call streams do not false-timeout. |
| `engineer_review_limit` | `3` | How many reviewer reruns the engineer workflow performs before asking you how to proceed | Lower it if you want to step in sooner on review disagreements. Raise it if you want more autonomous acceptance-criteria fixing. |
| `engineer_execution_retry_limit` | `6` | How many stalled-task nudges KodaCode injects before it asks you how to resolve execution stall | Lower it if you want earlier intervention on stuck tasks. Raise it if you trust the engineer to recover from temporary stalls without your help. |
| `max_subagents` | `10` | Maximum concurrent subagent sessions | Lower it to cap parallel spend and provider load. Raise it when wide parallel research or planning materially speeds up your workflow. |
| `subagent_timeout` | `5` minutes | How long a subagent can run before it is cancelled | Increase it for large audits, slower providers, or repo-wide analysis. Lower it if stale subagents are wasting time or budget. |
| `plan_approval` | `true` | Whether broad engineer workflows pause for approval before execution | Keep it on when you want a checkpoint before multi-step work. Turn it off when you want the engineer to plan and execute in one pass. |
| `background_auto_react` | `true` | Whether completed background bash jobs are automatically fed back to the model | Keep it on for test-fix loops and long-running commands. Turn it off if you want manual control over when background output re-enters the session. |
| `snapshot` | `false` | Whether file-changing turns create shadow git snapshots for `/replay` | Turn it on when you want time-travel, recovery, or safe state restoration without touching your working branch. |
| `trace` | `false` | Whether per-turn step traces are captured for `/cost`, `/trace`, and the traces API | Turn it on when you need to understand why a turn was slow or expensive, or to tune prompts, tool usage, and cost. |
| `budget` | `0` | Per-session spend cap in USD (`0` disables it) | Set it for experiments, CI runs, or provider testing where you want a hard stop before spend runs away. |
| `budget_warn` | `0` | Warning threshold for `budget` (`0` disables warnings) | Set it to something like `0.8` so you get an early heads-up before the session hard cap trips. |
| `total_budget` | `0` | Cross-session spend cap across persisted non-ephemeral sessions (`0` disables it) | Use it when many sessions or subagents share the same wallet and you want one global ceiling, not just per-session caps. |
| `total_budget_warn` | `0` | Warning threshold for `total_budget` (`0` disables warnings) | Set it to `0.8` or `0.9` to detect aggregate spend pressure before KodaCode starts forcing sessions to stop. |
| `primary_max_steps` | `250` | Maximum tool calls allowed in one primary-session turn | Lower it to stop runaway tool loops earlier and keep costs predictable. Raise it only if legitimate long-horizon tasks are being cut off too soon. |
| `subagent_max_steps` | `30` | Maximum tool calls allowed in one subagent turn | Lower it to keep research agents cheap and bounded. Raise it when a subagent needs more room to complete repo-wide exploration. |

### Per-model session overrides

Use `session.models` when different models need different guardrails. A frontier model may benefit from earlier compaction to keep spend down, while a local model may need more time to finish streaming tool-call JSON.

Keys are best written as `provider/model`. Bare model IDs still work as a compatibility fallback.

These entries are explicit user overrides, not hidden built-in model profiles. If you do not define a key under `session.models`, KodaCode uses the top-level `session` values for that model.

| Override | Practical Value |
|----------|-----------------|
| `compaction_threshold` | Compact earlier on expensive models to cap input cost, or later on cheaper models to preserve more raw history. |
| `compaction_keep_turns` | Preserve more recent context for models that lose track of short-term conversation state after compaction. |
| `prune_protect_tokens` | Keep more recent tool output intact for models that need direct evidence instead of compact summaries. |
| `prune_min_savings` | Make pruning more or less eager for specific models depending on context pressure tolerance. |
| `context_limit` | Stop weaker or smaller-context models earlier before they overflow or degrade. |
| `max_input_tokens` | Work around providers that cap usable input below the model's advertised context window. |
| `tool_call_argument_timeout` | Give slow local models longer to finish emitting tool-call JSON without penalizing faster cloud models. |

### Automatic compaction floor for smaller-context models

KodaCode applies one runtime safeguard even when `session.models` is empty:

- If a model's effective context window is below `256k`, `compaction_threshold` is raised to at least `0.60`.
- If a model's effective context window is below `64k`, `compaction_threshold` is raised to at least `0.70`.

Practical value: this prevents overly aggressive compaction on smaller-context models, where compacting too early can throw away useful recent working context. Explicit per-model overrides still apply, but values below this floor are raised to the minimum.

### Tool Call Argument Timeout

`tool_call_argument_timeout` only controls how long kodacode waits for the model to finish streaming one tool call's JSON arguments.

- It does not limit how long the tool itself may run.
- The default is `60s`, which is a reasonable general-purpose setting for hosted providers.
- LM Studio and Ollama users should expect to raise it for slower local models that emit tool-call JSON gradually.
- If a local model keeps tripping this limit, raise it globally under `session` or per model under `session.models`.
- If your hosted provider is consistently healthy, `60s` usually fails broken tool-call streams fast enough without being too aggressive.

### Engineer workflow controls

`max_retries`, `engineer_review_limit`, and `engineer_execution_retry_limit` cover different failure modes:

- `max_retries`
  - retries transient provider/API failures such as rate limits or temporary upstream errors
  - does not control engineer task review or execution-stall handling

- `engineer_review_limit`
  - controls how many times engineer will automatically retry reviewer verification for a task
  - default effective behavior is `3`

- `engineer_execution_retry_limit`
  - controls how many times KodaCode will inject "keep working" nudges for a stalled active task before asking you what to do
  - default effective behavior is `6`

The engineer workflow can ask these questions when it reaches a decision point:

1. `How would you like to proceed?`
   - `Save plan and proceed`
   - `Proceed without saving plan files`
   - `Reject plan`

2. `Reviewer retry limit reached. How should KodaCode proceed?`
   - `Continue fixing this task without more automatic reviews`
   - `Accept unresolved reviewer findings and proceed`
   - `Stop execution and wait for me`

3. `Execution is stalled on the current task. How should KodaCode proceed?`
   - `Keep working on the current task`
   - `Mark the current task blocked and stop`
   - `Stop and wait for me`

## TUI

```yaml
tui:
  input_max_height: 8       # max rows for input textarea
  theme: default             # theme name from ~/.config/kodacode/themes/
  display_turns: 4           # recent turns to keep rendered (0 = unlimited)
  error_display_time: 0      # seconds before error toast dismisses (0 = persist)
  auto_resume: false         # resume last session on startup instead of home screen
  max_attachment_size: 20971520  # max file attachment size in bytes (default: 20 MB)
```

| Field | Default | Description |
|-------|---------|-------------|
| `input_max_height` | `8` | Maximum height of the input textarea in rows |
| `theme` | `""` | Theme name from `~/.config/kodacode/themes/` |
| `display_turns` | `4` | Number of recent turns to render (0 = all) |
| `error_display_time` | `0` | Seconds before error toasts auto-dismiss (0 = persist until next action) |
| `auto_resume` | `false` | Skip home screen and resume last session |
| `max_attachment_size` | `20971520` | Maximum file attachment size in bytes (default: 20 MB) |

### Themes and Syntax Highlighting

Each theme file in `~/.config/kodacode/themes/` can specify a `syntax_style` to control code block highlighting. This maps to a [chroma](https://github.com/alecthomas/chroma) style name:

```yaml
# ~/.config/kodacode/themes/my-theme.yaml
name: my-theme
syntax_style: dracula        # any valid chroma style name

palette:
  primary: "#bd93f9"
  surface: "#282a36"
  text: "#f8f8f2"
  # ...
```

If `syntax_style` is omitted, kodacode picks one automatically based on the theme name or palette brightness.

| Theme | `syntax_style` |
|-------|---------------|
| Catppuccin Mocha | `catppuccin-mocha` |
| Dracula | `dracula` |
| Gruvbox Dark | `gruvbox` |
| Nord | `nord` |
| One Dark | `onedark` |
| Rosé Pine Moon | `rose-pine-moon` |
| Solarized Dark | `solarized-dark` |
| Tokyo Night | `tokyonight-night` |
| Any light theme | `github` |

Browse the [chroma style gallery](https://xyproto.github.io/splash/docs/) to preview available styles.

## Permissions

```yaml
permission:
  bash:
    "*": ask
    "ls *": allow
    "go test *": allow
    "rm *": deny
  read:
    "*": allow
    "*.env": deny
    "*.env.example": allow
  write: ask
  edit: allow
  glob: allow
  grep: allow
```

Permission rules are merged across layers (defaults → global → project → agent) at the **pattern level**. Patterns from each layer are appended in order, and the last matching pattern wins. This means a project config can override specific globs without losing patterns from earlier layers.

For example, if defaults define `read: { "*": allow, "*.env": ask }` and a project config adds `read: { "*.env": deny }`, the merged result is `[* → allow, *.env → ask, *.env → deny]`. The project's deny wins for `.env` files, while the default catch-all allow remains in place for other files.

String shorthand (e.g. `bash: allow`) is expanded to `* → allow` before merging.

See [Permissions](/features/permissions/) for full documentation.

## LSP Servers

Three servers are configured by default (`gopls`, `vtsls`, `pyright`). Additional servers are auto-discovered from your project. Servers start on demand, so the first query to a matching file extension starts the server.

```yaml
lsp:
  servers:
    - name: gopls
      command: gopls
      extensions: [".go"]
      env:
        GOFLAGS: "-mod=mod"
    - name: vtsls
      command: vtsls
      args: ["--stdio"]
      extensions: [".ts", ".tsx", ".js", ".jsx"]
    - name: pyright
      command: pyright-langserver
      args: ["--stdio"]
      extensions: [".py", ".pyi"]
    - name: rust-analyzer
      command: rust-analyzer
      extensions: [".rs"]
      enabled: true              # set false to disable
```

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Unique server identifier |
| `command` | Yes | Executable command |
| `args` | No | Command-line arguments |
| `env` | No | Additional environment variables |
| `extensions` | Yes | File extensions this server handles |
| `enabled` | No | Set `false` to disable (default: `true`) |

Project-local `kodacode.yaml` entries merge with global `lsp.servers` by `name`. Matching servers are overridden field-by-field, so you can disable or tweak one inherited server without re-declaring the rest.

## MCP Servers

```yaml
mcp:
  servers:
    - name: filesystem
      type: stdio
      command: npx
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/path"]
      env:
        NODE_ENV: production
    - name: github
      type: stdio
      command: npx
      args: ["-y", "@modelcontextprotocol/server-github"]
      env:
        GITHUB_PERSONAL_ACCESS_TOKEN: ${GITHUB_TOKEN}
    - name: custom-sse
      type: sse
      url: https://example.com/mcp
      headers:
        Authorization: Bearer ${MCP_TOKEN}
      enabled: true              # set false to disable
```

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Unique server name |
| `type` | Yes | `stdio` or `sse` |
| `command` | stdio | Command to run |
| `args` | No | Command arguments |
| `url` | sse | SSE endpoint URL |
| `headers` | No | HTTP headers (SSE only) |
| `env` | No | Environment variables (stdio only) |
| `enabled` | No | Set `false` to disable (default: `true`) |

See [MCP Integration](/features/mcp/) for setup details.

## Skills

```yaml
skills:
  models:
    "openai/gpt-4o":
      allow_all: true         # allow all skills for this model
      deny: ["dangerous-skill"]  # except these
```

Project-local `skills.models` entries merge by model key. `allow_all` uses the project value when set, while `deny` lists are appended uniquely so project config can further restrict a globally allowed model.
